Where the API history falls short

Found while pulling the data above. Each one is a reason not to rely on the API alone.

Early allocation sits one level down

Until 23 April 2026 the vault's MetaMorpho adapter 0xFc98…043C held shares of Steakhouse USDC (V1), which lent to the markets. The API keeps that position and the V1 vault's per-market history, so the vault's share of each market can be rebuilt exactly, but only by joining the two. Returns in that period were also net of the V1 vault's own performance fee (5% today; the API's fee history for it has no usable points, so check it on-chain).

No liquidity history

Instant liquidity and force-deallocatable liquidity exist only as current values. If you care how quickly depositors could exit on a given day, you have to record it that day.

The schema changes without notice

Between January and October 2026 the API removed or renamed dozens of fields, which broke every query in this repo. Stored snapshots keep their meaning even when the API changes.

Query limits shape the backfill

APY lookbacks stop at 24 hours, list queries stop at 10,000 skipped rows, and deep queries hit a complexity cap. Longer windows have to be computed from share price, and flows have to be paged by time window.

Recommended setup

Backfill once from the API, record your own snapshot every day, and use the chain to verify and fill gaps. The API gives you a year of history in minutes, but some numbers exist there only as today's value, and its schema changes without notice. Your own daily table is the record that lasts. On-chain reads are the ground truth when the two disagree.

  1. Backfill from the API

    Pull vault, market and adapter-position timeseries at interval: DAY, and page deposits and withdrawals in 30-day windows. This covers everything marked “Full history” above.

  2. Add a daily snapshot command to this repo

    A morpho history snapshot command reuses the existing API client and writes one row per table per day. Run it from cron or a systemd timer shortly after 00:00 UTC so days line up with the API's own points.

  3. Verify against the chain

    At the first block of each day, read convertToAssets on the vault and the adapter's position in each market through an archive RPC. The repo already has the ERC-4626 client for the first read.

  4. Look through nested vaults

    When an adapter holds another vault's shares, record its position in that vault and that vault's per-market allocation, then split pro rata. This rebuilds November to April for this vault and covers any future vault-in-vault adapter.

-- one row per UTC day
vault_daily(
  day, total_assets, total_supply, share_price,
  idle_assets, liquidity, force_dealloc_liquidity,
  tvl_usd, api_net_apy, perf_fee, mgmt_fee
)
allocation_daily(
  day, adapter, via_vault, market_id, supply_assets,
  supply_usd, cap_absolute, cap_relative
)
market_daily(
  day, market_id, supply_usd, borrow_usd,
  utilization, supply_apy, borrow_apy, liquidity_usd
)
flows_daily(
  day, deposits, withdrawals, deposit_count,
  withdraw_count, depositors, top10_share
)
-- one row per change, from snapshot diffs
config_events(
  ts, kind, detail  -- curator, allocator, cap,
)                   -- fee, gate, adapter changes
